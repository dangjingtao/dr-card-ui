# 卡博士 Mockplus → UI → 实现｜实际评估与 15 张任务卡

> 评估日期：2026-08-21
> 评估原则：以仓库、可运行页面和 Mockplus 离线包为证据，不继承此前“自审通过”的结论。

## 1. 项目目标

整个项目要完成的不是一张首页，也不是一套静态组件，而是：

> 将「卡博士诗得丽」Mockplus 原型中的有效业务页面，转化为有明确设计依据、具备完整状态与交互、可运行且可验收的移动端 UI 实现。

事实源优先级遵循 `AGENTS.md`：当前任务中的用户确认 > 已确认 Mockplus 原型 > 原型说明 > Com Design 与已确认实现 > 历史参考 > 智能体推断。

## 2. 本次实际盘点

### 2.1 原型范围

- Mockplus 页面树共 72 个节点。
- 其中 60 个节点进入实现任务卡。
- 12 个节点进入“暂缓/旧稿/试验范围关闭”，不默认施工：`#1、#3、#9、#10、#31、#45–#47、#50–#53`。
- 14 个历史任务、约 15 个界面存在未确认重设计风险，必须先完成对应决策，不得直接照搬。

### 2.2 当前代码事实

- 当前路由注册表覆盖 60 个实施节点；五个主导航种籽页为 `/`、`/points`、`/card/verify`、`/membership`、`/profile`，详见 [`evidence-matrix.md`](./evidence-matrix.md) §2 与 [`route-table.md`](./route-table.md)。`/checkin` 是打卡二级页，不是泡泡 Tab。
- owner 于 2026-08-24 确认当前仓库实现、路由和页面状态为正确事实源；此前种籽页等级快照仅作历史记录。
- `/card` 与 `/exchange` 是保留的二级可达路径，`/draw-success` 已重定向至 `/luck/result`；不再采用此前“5 条旧路由”的盘点口径。
- 33 个 Com Design 名称已经导出，但大部分只是集中实现的入口文件；尚无页面级覆盖、状态矩阵、交互与可访问性证据。
- TypeScript 类型检查和生产构建可以通过；这只能证明工程可编译，不能证明页面、视觉或交互已完成。

### 2.3 对此前任务规划的判定

此前 T001–T015 只有“任务名 + 一句说明”，存在以下问题：

- 没有精确对应 72 个原型节点，无法证明全量覆盖。
- 没有区分已确认页面、历史冲突页面和明确暂缓页面。
- 没有记录当前代码真实差距，容易把占位页判成完成。
- 没有依赖、阻塞决策、状态矩阵、路由和交互目标。
- “Build 通过”被错误地当成整体验收。
- “全量页面适配整理”是一张无法独立验收的兜底卡。
- 智能体自审与用户验收没有分开。

因此，旧任务表不再作为完成度依据；以下 15 张卡全部重新定义。

## 4. 覆盖校验

实施任务 T005–T013 共覆盖 60 个节点：

```text
9 + 9 + 9 + 8 + 9 + 4 + 4 + 4 + 4 = 60
```

T014 覆盖其余 12 个范围关闭节点：

```text
60 个实施节点 + 12 个暂缓/旧稿/试验节点 = 72 个 Mockplus 页面节点
```

任何页面不得同时遗漏于两类范围之外，也不得在没有决策记录时从 T014 偷渡到实现任务。

## 5. 验收结论规则

- 智能体完成自检后只能进入 `User Review`，不能自行标记 `Accepted`。
- `npm run typecheck` 和 `npm run build` 是必要条件，不是页面通过的充分条件。
- 页面卡必须提供 375 × 812 的实现截图、对应原型证据、差异说明、交互结果和路由。
- 多状态页面必须提交状态矩阵；只展示默认态不能通过。
- 交互必须验证触发器、动作、目标与返回路径；视觉上像按钮不算已实现。
- 命中历史冲突或原型缺口时，必须先形成决策记录，再继续该页面。
- 最终是否过关，以用户验收为准。
