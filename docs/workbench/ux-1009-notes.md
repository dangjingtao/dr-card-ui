## UX-02｜品牌福利官二维码长按保存（H5 优先）

- **用户反馈：** 「长按可以调用保存吗？我希望是h5端做」。
- **定位：** `src/pages/WelfareOfficer.tsx` 中 `WelfareQrImage`。
- **已核实：** 当前仅使用 `<img src={config.qrcodeUrl}>` 展示后台配置的二维码，并显示「长按或扫描二维码，联系福利官」；页面没有明确的 H5 长按手势、保存操作或保存结果反馈。
- **产品意图：** 用户长按二维码时能够发起保存；**优先由 H5 负责交互及图片导出 / 下载**，尽量不要求 Native 新增能力。
- **建议待验证交互（尚未定稿 / 未实现）：** H5 长按手势 → 「保存二维码 / 取消」操作菜单 → 生成或获取可保存 PNG → 发起保存，并明确提示成功或失败。
- **实现风险与验收边界：**
  - H5 能处理长按，不等于 Android / iOS App WebView 一定能将文件保存到系统相册。
  - 需要核实二维码图片的来源、跨域 / CORS、下载或 Canvas 导出可行性，及长按和系统默认菜单冲突。
  - 必须用当前 Android App WebView 验证用户可在设备上实际找到并打开所保存的图片，不能以浏览器触发下载或弹出 Toast 当作成功；iOS 需另行验证。
  - 仓库 `docs/workbench/tasks/H032-native-media-share.md` 已定义 `saveImageToAlbum` 的 Native 目标协议，但文档称 Native 尚未实现。因此它只能作为后续需要时的已有契约参考，**不能当作现成可用能力，更不能预设本轮要接原生**。
- **不在范围：** 本次不调整福利官 API、二维码数据或页面文案，不增加 JSBridge、不改 Native 代码。

## UX-03｜泡泡任务区混入未落地的占位任务与虚构奖励

- **用户反馈：** 泡泡值页面「这里是不是有一部分假任务」，现场截图出现「每日签到 1/31」「观看视频 +5 🫧 0/1」「邀请好友 +50 🫧 0/1」。
- **定位：** `src/pages/Points.tsx` 的 `taskCards` 列表拼装，以及 `src/app/fixtures/membership.ts` 的 `POINTS_TASK_PLACEHOLDERS`。
- **已核实：**
  - 「每日签到」等签到类活动从 `GET /api/signactivity/list` 读取标题、签到天数和目标天数，界面具备真实 API 接线；签到动作由 `POST /api/signrecords/add` 等接口负责。是否完成业务验收仍需独立确认。
  - 「观看视频」是静态 Fixture：奖励 `+5`、进度 `0/1`、未开始；「邀请好友」也是静态 Fixture：奖励 `+50`、进度 `0/1`、未开始。两项在当前泡泡任务列表没有对应的数据源或完成/结算链路，任务卡本身也不是可点击交互。
  - `Points.tsx` 注释明确说明这两项「继续读 fixtures 占位」，但 2026-09-29 变更曾主动移除面向用户的「占位」标签，导致生产样式中呈现为似乎可以获得泡泡值的正式任务。
  - 顶部余额、累计收入和累计消耗读取独立的 `GET /api/userpoints/stat`，不应与这两项假任务混为一谈。
- **产品风险：** 用户可能合理认为「观看视频 +5」「邀请好友 +50」是已开放并可以兑现的奖励承诺；实际缺失任务入口、进度真相和奖励结算，存在误导。
- **后续处理方向（未施工）：** 正式 H5 在真实任务能力未落地前，不应把这两项当可完成、可领奖的任务呈现。具体采用「先隐藏占位任务」还是「业务立项并由后台提供完整任务/进度/发奖契约后开放」，留待后续产品与后台联调确认；不在本轮臆造 API 或奖励规则。保留已接通的真实签到活动。
- **待验证：** 真实 App 的 API 模式与 `GET /api/signactivity/list` 实际返回；后台是否另有尚未接入的任务系统；用户签到后任务进度与积分流水是否一致；奖励真实结算与防重复领取机制；正式发布状态。

## UX-05｜个人中心 / 资料设置页默认头像改为中性灰白色人头 SVG

- **用户反馈：** 「默认的头像/加载中能否换成灰白色人头svg。目测这张女人头像非常非常大。」现场截图为「会员中心」（实际上是底部会员中心 Tab 的 `src/pages/Profile.tsx` 页面，不是 `src/pages/Membership.tsx` 的会员等级中心）。
- **已核实实现：**
  - `src/pages/Profile.tsx` 引用 `src/assets/brand/home/home-avatar.webp` 作为 `avatarFallback`，`avatarSrc = profile?.avatar ?? avatarFallback`。因此资料未返回、头像未配置时都会显示照片；远程头像加载出错时当前 `img` 没有 `onError` 可用回退。
  - `src/pages/Settings.tsx` 也引用同一张照片作为 `useState(avatar)` 初始头像；当前页面读取 `GET /api/user/detail`，它仅包含昵称 / 年级相关资料，并没有真实头像字段，因此资料设置页展示照片并不能代表已经拿到了用户真实头像。后续处理不得把本地选择但未持久化的图片直接冒充后台头像。
  - 仓库中的 `home-avatar.webp` GitHub 文件元数据大小约 193,764 字节（约 194 KB，十进制）；个人中心页面头像容器为 `h-16 w-16`（64×64 CSS px），且附带装饰描边 / halo。**文件体积**和**屏幕视觉大小**是两个独立问题。
  - 公共 `src/components/ui/Avatar.tsx` 已存在（代理 `ComDesign.tsx` 的 `Avatar`，无图时展示姓名缩写 / 圆点）；尚无本需求指定的统一灰白人头 SVG 缺省样式。施工前优先判断扩展公共组件还是提供共享本地 SVG 素材，避免页面重复画图。
  - `GET /api/user/profile` 返回真实 `avatar_img`，由 `src/services/userProfile.ts` 解析成可选 `avatar`；已有真实头像必须保留。
- **后续产品意图（未施工）：** 将默认照片替换为**灰白色中性人头 SVG**。加载中 / 无头像 / 图片失效时展示相同占位图，背景浅灰白、图形居中且视觉比现有女性照片更克制；可沿用头像容器并适度收敛图标视觉大小，不擅自改变个人中心整体布局或遮挡点击编辑入口。
- **边界与注意：** 真实用户已设置的头像仍正常显示；失败回退不能造成无限重试或闪图；头像占位语义和尺寸在个人中心、资料设置页一致。不得引入随机真人照片、头像 mock 或将临时本地图片当成服务器已保存的真实头像。
- **验收关注：** Android WebView 加载中 / 无真实头像 / 真实头像 / 失效 URL 四种状态；资料设置页默认图一致；快速进出页面不闪女性默认照片；透明 SVG 对比度与高 DPI 清晰度；头像点击和资料编辑入口正常。
- **本轮范围：** 仅补小本本，不生成新 SVG 资源，不改业务代码，不验收。

## UX-07｜通知筛选 Tab 背景与滚动定位整改

- **用户反馈：** 「通知模块，tab 背景不应该是白色。。。也不应该随页面滚动。」截图红框强调「全部 / 未读 / 推送 / 活动」筛选栏；希望筛选栏留在顶部、消息列表滚动。
- **定位与根因（已核实）：**
  - `src/pages/Notifications.tsx` 的 Tab 外层容器写死 `bg-white border-b border-divider px-4 pt-3 pb-1`；`SegmentedControl` 组件来自 `src/components/ui/ComDesign.tsx`，默认 track 为 `bg-surface-subtle`，选中项为 `bg-surface`（白色）。两层配色叠加，造成与暖色页面底不一致的白色横带。
  - `src/layouts/MobileLayout.tsx` 的 `[data-page-scroll]` 是整条业务页面的 `overflow-y-auto` 滚动容器，`Notifications.tsx` 中 Tab 和列表都包在 `PageContainer` 下；当前外层的 `shrink-0` 在此布局中不是吸顶规则，Tab 因而跟着整个页面移动。
  - `preview` 与 `dev` 的 `Notifications.tsx` 当前均使用这套静态结构，不能将其描述为已实现 sticky。
- **待实施视觉方向：** Tab 区外层背景与项目页面暖色背景 / 设计 Token 对齐，取消生硬纯白色底；SegmentedControl 的选中项也应采用协调的浅品牌色或其它经当前视觉基线认可的高对比设计（不能仅改外层、留下显眼白块），保留数字 badge 的可读性。不因局部修复把全局共用 SegmentedControl 的其它页面误改。
- **待实施滚动交互：** 通知 TitleBar 仍由壳层固定在最上方；筛选栏吸顶于 TitleBar **下方**，列表本身照常滚动。优先评估在现有 `[data-page-scroll]` 下为本页 Tab 容器使用 `sticky top-0 z-...` 与不透明的非白色背景，若 WebView / 路由容器约束造成 sticky 失效，再考虑局部滚动结构，不要为此重写全局 MobileLayout。避免通知卡片滚动穿透到 Tab 上方，也不遮挡标题或系统安全区。
- **验收关注：** Android App WebView 长列表上下滚动时 Tab 稳定停在标题栏下方；切换四类 Tab 后位置正确，尤其列表变短、空状态、不同未读数量和重进页面；横向溢出、小屏尺寸、路由返回和滚动恢复不异常；筛选、打开详情、全部已读与 badge 逻辑不回归；对比 `preview` 的视觉事实源。
- **边界：** 此轮仅登记 UX 问题，**不修改样式 / 页面 / 全局壳层代码，不新增功能，不验收、不合并**。

### UX-07 补充｜成熟 Tab + 列表交互与空态规范（2026-10-09 用户追加）

- **用户追加要求：** 「通知模块，交互/空页面 都是看参照其它的成熟的tab + 列表处理。」此要求属于 **UX-07 的范围补充**，不新增独立编号，不要求本轮马上施工。
- **参考规范（成熟模式，不直接照抄品牌样式）：**
  - [Android Material Components / Material 3 Tabs](https://github.com/material-components/material-components-android/blob/master/docs/components/Tabs.md)：Tabs 在同一页面、同级内容中切换；位于顶部 App Bar 下方，选中状态清晰，数量少时维持固定位置。
  - [Ant Design / Empty Status](https://ant.design/docs/spec/research-empty/?locale=en-US)：无数据、完成 / 清空等空状态应表达不同语义，不都用一个泛化的「暂无内容」；仅提供真实可执行的下一步操作。
  - [Ant Design / Empty](https://ant-design.antgroup.com/components/empty)：复用现有视觉规范中的空状态组件和语义，不为某个 Tab 另造样式。
  - **项目内落地原则：** 不添加新的 UI 框架、不复制第三方代码；复用 `src/components/ui/EmptyState.tsx`、现有 Tab 与项目设计 Token，保持原页面视觉基线。
- **交互规则（待施工验收）：**
  1. 顶部 `TitleBar` 和紧随其下的四个筛选 Tab 固定，**滚动只改变下方通知列表**。长列表、短列表、空状态在同一个内容区替换，不使 Tab 跟着移动；对已有 H5 滚动恢复机制做局部兼容。
  2. 点击 `全部 / 未读 / 推送 / 活动` 时，选中态、列表内容、计数同步更新；无论列表滚到何处，切换后应从新列表顶部开始，避免短列表继承上一分类的长距离滚动偏移。返回通知详情后是否恢复原 Tab 和滚动位置，优先遵循当前 H5 导航/滚动恢复契约并核实 App WebView 行为，不擅自引入全局状态机制。
  3. 横向滑动切换 Tab **不是默认必做**：可以参照成熟方案评估，但不得与通知列表的纵向滚动、原生边缘返回、系统手势冲突，也不应为了「像其他 App」额外引入复杂滑动实现。
  4. 任何分类没有结果，Tab 仍保持固定且可切换；统一空态组件位置与高度，不使页面骤然塌缩。空态文案需区分「全部为空：暂无通知」「未读为空：消息都已读完」「推送/活动无结果：暂无相关通知」；允许随具体分类使用更贴切的短句，但不暗示数据已删除或系统故障。
  5. 将 `loading / normal / empty / error` 作为未来 API 接入时的完整显示状态矩阵。没有真实加载/错误状态的数据源时，不虚构等待、刷新成功；真实报错才提供真实可用的「重试」，必要时保留已加载内容避免不必要整屏闪烁。
  6. **不呈现虚假的可执行提示。** 当前 `Notifications.tsx` 的空态写着「下拉刷新看看」，但页面没有与之对应的下拉刷新处理，后续必须删掉这句或在明确真实刷新机制后再展示。不能用单纯页面重新渲染充当业务刷新。
  7. 计数与操作按真相展示：现有「全部」badge 在有未读时用未读数、无未读时用总数，语义会变化；需要统一确定是总数还是未读数，不可在同一 badge 中隐式切换口径。标记全部已读后，未读页及时显示已读完成空态；内容分类与消息详情的状态回写保持一致。
- **现状风险隔离：** `src/app/state/notifications.ts` 明确声明内容来自 `NOTIFICATION_FIXTURES`，已读仅为会话内 Zustand 状态，刷新后恢复夹具初始状态。它不是已接真实消息列表或远程已读写入的证据。**本 UX 卡只记录 UI 期望，不擅自发明通知后台 API、未读持久化或手势刷新能力**；是否接真实服务另行依据已确认工程契约处理。
- **验收矩阵：** 全部有消息 / 全部空；未读有消息 / 全部已读；推送空 / 活动空；长列表滚动、短列表切换、返回详情；Badge 数量变化、全部已读、禁用操作；Android WebView 的顶部固定、快速切换、防横纵手势冲突、可访问性焦点；如接入 API，再覆盖加载、报错、重试。原有四 Tab 分类口径先保持，不因参考规范自动变成二 Tab（原型中该数量仍有历史冲突记录）。
- **本轮边界不变：** 只追加规范到 UX 小本本；无业务代码、无样式或测试代码修改，不宣布功能完成。
