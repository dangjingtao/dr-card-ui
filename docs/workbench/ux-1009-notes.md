## UX-01｜卡包空状态未复用项目统一组件

- **用户反馈：** 「这个页面好像没用项目自身的空状态UI」。
- **定位：** `src/pages/Card.tsx` 的三个 Tab（可用 / 已使用 / 已过期）；公共空状态位于 `src/components/ui/EmptyState.tsx`，由 `ComDesign.tsx` 实现。
- **已核实：** `dev` 的卡包零数据状态自行组合 `div`、票券图标、标题和说明，没有使用 `EmptyState`；加载中和加载失败也有类似的页面内自绘内容。现有单测只断言空态文案存在，未防止组件复用回退。
- **后续处理方向（未施工）：** 优先复用现有设计系统组件，保留三类状态的业务文案与图标，不动卡包 API、数据和 Tab 逻辑；评估加载 / 错误状态按现有公共模式收敛，补三个 Tab 与错误态相关回归。
- **待验证：** 设计基线及 375×812 视觉；空数据、加载失败和正常券列表切换；Android App WebView 中的实际效果。

## UX-02｜品牌福利官二维码长按保存（H5 优先）

- **用户反馈：** 「长按可以调用保存吗？我希望是h5端做」。
- **定位：** `src/pages/WelfareOfficer.tsx` 中 `WelfareQrImage`。
- **已核实：** 当前仅使用 `<img src={config.qrcodeUrl}>` 展示后台配置的二维码，并显示「长按或扫描二维码，联系福利官」；页面没有明确的 H5 长按手势、保存操作或保存结果反馈。
- **产品意图：** 用户长按二维码时能够发起保存；**优先由 H5 负责交互及图片导出 / 下载**，尽量不要求 Native 新增能力。
- **建议待验证交互（尚未定稿 / 未实现）：** H5 长按手势 → 「保存二维码 / 取消」操作菜单 → 生成或获取可保存 PNG → 发起保存，并明确提示成功或失败。
- **实现风险与验收边界：**
  - H5 能处理长按，不等于 Android / iOS App WebView 一定能将文件保存到系统相册。
  - 需要核实二维码图片的来源、跨域 / CORS、下载或 Canvas 导出可行性，及长按和系统默认菜单冲突。
  - 必须用当前 Android App WebView 验证用户可在设备上实际找到并打开所保存的图片，不能以浏览器触发下载或弹出 Toast 当作成功；iOS 需另行验证。
  - 仓库 `docs/workbench/tasks/H032-native-media-share.md` 已定义 `saveImageToAlbum` 的 Native 目标协议，但文档称 Native 尚未实现。因此它只能作为后续需要时的已有契约参考，**不能当作现成可用能力，更不能预设本轮要接原生**。
- **不在范围：** 本次不调整福利官 API、二维码数据或页面文案，不增加 JSBridge、不改 Native 代码。

## UX-03｜泡泡任务区混入未落地的占位任务与虚构奖励

- **用户反馈：** 泡泡值页面「这里是不是有一部分假任务」，现场截图出现「每日签到 1/31」「观看视频 +5 🫧 0/1」「邀请好友 +50 🫧 0/1」。
- **定位：** `src/pages/Points.tsx` 的 `taskCards` 列表拼装，以及 `src/app/fixtures/membership.ts` 的 `POINTS_TASK_PLACEHOLDERS`。
- **已核实：**
  - 「每日签到」等签到类活动从 `GET /api/signactivity/list` 读取标题、签到天数和目标天数，界面具备真实 API 接线；签到动作由 `POST /api/signrecords/add` 等接口负责。是否完成业务验收仍需独立确认。
  - 「观看视频」是静态 Fixture：奖励 `+5`、进度 `0/1`、未开始；「邀请好友」也是静态 Fixture：奖励 `+50`、进度 `0/1`、未开始。两项在当前泡泡任务列表没有对应的数据源或完成/结算链路，任务卡本身也不是可点击交互。
  - `Points.tsx` 注释明确说明这两项「继续读 fixtures 占位」，但 2026-09-29 变更曾主动移除面向用户的「占位」标签，导致生产样式中呈现为似乎可以获得泡泡值的正式任务。
  - 顶部余额、累计收入和累计消耗读取独立的 `GET /api/userpoints/stat`，不应与这两项假任务混为一谈。
- **产品风险：** 用户可能合理认为「观看视频 +5」「邀请好友 +50」是已开放并可以兑现的奖励承诺；实际缺失任务入口、进度真相和奖励结算，存在误导。
- **后续处理方向（未施工）：** 正式 H5 在真实任务能力未落地前，不应把这两项当可完成、可领奖的任务呈现。具体采用「先隐藏占位任务」还是「业务立项并由后台提供完整任务/进度/发奖契约后开放」，留待后续产品与后台联调确认；不在本轮臆造 API 或奖励规则。保留已接通的真实签到活动。
- **待验证：** 真实 App 的 API 模式与 `GET /api/signactivity/list` 实际返回；后台是否另有尚未接入的任务系统；用户签到后任务进度与积分流水是否一致；奖励真实结算与防重复领取机制；正式发布状态。

## UX-04｜会员中心「尊享服务」金刚区跟随真实会员等级主题

- **用户反馈：** 「下方金刚区的配色能否跟随真实会员系统更新一下。」截图中会员卡为玫瑰粉，下面「尊享服务」四入口却统一黑金，视觉割裂。
- **定位：** `src/pages/Membership.tsx`，上方卡面读取 `useProfileFeed()` 的 `gradeId` 并用 `getMemberCardTheme(profile?.gradeId)`；下方 `MEMBER_ENTRIES` 四入口仍使用固定 `var(--gradient-bubble)`、`var(--gradient-member)`、`text-member-accent`，不依等级切换。
- **已核实数据真相：**
  - `GET /api/user/profile` 已提供用户 `grade_id`，H5 解析为 `gradeId`；上方卡面已经依此选择主题。
  - `src/pages/membership/memberCardTheme.ts` 当前按后台已确认的等级 ID `1/2/3/4` 映射玫瑰粉 / 薰衣草紫 / 海洋蓝 / 翡翠绿（第四级配香槟金强调）；未知或缺失等级走中性 `UNASSIGNED_MEMBER_CARD_THEME`，不可冒充高级会员。
  - `GET /api/usergrade/index` 提供真实等级列表、名称等信息，但当前服务契约没有明确规定后台下发可直接使用的颜色 Token；这次应复用 H5 现有卡面主题映射，不凭等级名称、数组顺序或 Fixture 再造等级。
- **后续设计方向（未实施）：** 四个入口的图标、圆形底色 / 边线随当前 `gradeId` 一起采用会员卡同源配色。优先扩充 / 复用已有 `MemberCardTheme` 的可读语义，而不是把每级颜色在 `Membership.tsx` 再复制一份；对比度、按压态和中性回退都要照顾到。保持四入口内容、布局、导航与权限业务不变，**只调视觉**，不把等级颜色暗示成某权益已经开通。
- **建议主题方向（待 UI 对照验收）：** 1 玫瑰粉 / 酒红；2 薰衣草紫 / 紫；3 海洋蓝 / 蓝灰；4 翡翠绿 / 香槟金。配色来自当前会员卡视觉；图标具体背景、描边强度与对比度以最终 375×812 及 Android WebView 视觉为准。
- **验收关注：** 四个真实等级、加载中、未知 / 缺失等级；卡面与金刚区主题一致；文字可读 / 图标对比度；四个入口点击及路由无回归。
- **本轮范围：** 仅记录，不修改任何样式、设计 Token、服务契约或业务代码。

## UX-05｜个人中心 / 资料设置页默认头像改为中性灰白色人头 SVG

- **用户反馈：** 「默认的头像/加载中能否换成灰白色人头svg。目测这张女人头像非常非常大。」现场截图为「会员中心」（实际上是底部会员中心 Tab 的 `src/pages/Profile.tsx` 页面，不是 `src/pages/Membership.tsx` 的会员等级中心）。
- **已核实实现：**
  - `src/pages/Profile.tsx` 引用 `src/assets/brand/home/home-avatar.webp` 作为 `avatarFallback`，`avatarSrc = profile?.avatar ?? avatarFallback`。因此资料未返回、头像未配置时都会显示照片；远程头像加载出错时当前 `img` 没有 `onError` 可用回退。
  - `src/pages/Settings.tsx` 也引用同一张照片作为 `useState(avatar)` 初始头像；当前页面读取 `GET /api/user/detail`，它仅包含昵称 / 年级相关资料，并没有真实头像字段，因此资料设置页展示照片并不能代表已经拿到了用户真实头像。后续处理不得把本地选择但未持久化的图片直接冒充后台头像。
  - 仓库中的 `home-avatar.webp` GitHub 文件元数据大小约 193,764 字节（约 194 KB，十进制）；个人中心页面头像容器为 `h-16 w-16`（64×64 CSS px），且附带装饰描边 / halo。**文件体积**和**屏幕视觉大小**是两个独立问题。
  - 公共 `src/components/ui/Avatar.tsx` 已存在（代理 `ComDesign.tsx` 的 `Avatar`，无图时展示姓名缩写 / 圆点）；尚无本需求指定的统一灰白人头 SVG 缺省样式。施工前优先判断扩展公共组件还是提供共享本地 SVG 素材，避免页面重复画图。
  - `GET /api/user/profile` 返回真实 `avatar_img`，由 `src/services/userProfile.ts` 解析成可选 `avatar`；已有真实头像必须保留。
- **后续产品意图（未施工）：** 将默认照片替换为**灰白色中性人头 SVG**。加载中 / 无头像 / 图片失效时展示相同占位图，背景浅灰白、图形居中且视觉比现有女性照片更克制；可沿用头像容器并适度收敛图标视觉大小，不擅自改变个人中心整体布局或遮挡点击编辑入口。
- **边界与注意：** 真实用户已设置的头像仍正常显示；失败回退不能造成无限重试或闪图；头像占位语义和尺寸在个人中心、资料设置页一致。不得引入随机真人照片、头像 mock 或将临时本地图片当成服务器已保存的真实头像。
- **验收关注：** Android WebView 加载中 / 无真实头像 / 真实头像 / 失效 URL 四种状态；资料设置页默认图一致；快速进出页面不闪女性默认照片；透明 SVG 对比度与高 DPI 清晰度；头像点击和资料编辑入口正常。
- **本轮范围：** 仅补小本本，不生成新 SVG 资源，不改业务代码，不验收。
