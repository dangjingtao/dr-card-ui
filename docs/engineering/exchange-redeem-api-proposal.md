# 体验包兑换接口建议（后端最小实现）

> 状态：**Proposal / 待后端确认**
>
> 日期：2026-09-29
>
> 目标：给当前“泡泡值兑换通用体验包”提供一个正式业务动作接口。本文是 H5 侧对后端的**最小建议**，不是要求重构现有优惠券、积分或卡包模型。

## 1. 当前业务事实

历史设计里，体验券兑换专区支持多分类、多券模板；当前页面仍保留这套 UI 结构，便于未来恢复多体验券时继续使用。

但**当前真实业务只开放一个可兑换对象：通用体验包**。

因此：

- 当前不要求后端实现完整“多 SKU 兑换商城”；
- 不要求新增分类系统、库存中心、兑换订单体系或规则引擎；
- 页面保留多分类 / 多卡片结构，不代表当前后端必须提供多商品兑换能力；
- 现有 `GET /api/coupons/index` 继续承担券模板读取；
- 真正“扣泡泡值 + 写入卡包”由一个正式业务 action 完成。

## 2. 建议接口

### POST `/api/coupons/redeem`

需要登录：

```http
Authorization: Bearer <accessToken>
Content-Type: application/json
```

请求：

```json
{
  "coupon_id": 123
}
```

字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `coupon_id` | number | 是 | `coupons` 券模板主键 |

H5 不传：

- `user_id`
- 扣减后的积分
- 卡包记录字段
- 分类 id
- 商品价格副本

这些都由服务端根据当前登录用户和券模板决定，避免客户端篡改。

## 3. 当前唯一开放规则

当前仅允许兑换“通用体验包”。

最小实现可以在服务端配置或常量中指定当前允许兑换的 `coupon_id`，**不要求为了这一期新增表或新增字段**。

收到其它 `coupon_id` 时直接按业务失败返回，例如：

```json
{
  "code": 400,
  "message": "当前体验包不可兑换",
  "data": []
}
```

以后如果恢复多体验券，只需要把“哪些 coupon 可兑换”的判断扩展为现有表字段 / 配置，不需要修改 H5 请求结构。

## 4. 服务端一次事务内完成

建议该接口在一个事务里完成现有能力的组合：

1. 读取并校验券模板；
2. 确认该券当前允许兑换；
3. 校验上架 / 数量 / 现有业务限制；
4. 校验当前用户泡泡值余额；
5. 按现有积分规则扣减泡泡值并写积分明细；
6. 按现有卡包模型写入 `usercards`；
7. 更新已有兑换数量字段（如当前业务需要）；
8. 提交事务后返回结果。

重点是“扣积分”和“发卡”必须一起成功或一起失败，避免出现：

- 泡泡值扣了但卡没进卡包；
- 卡已发但积分没有扣；
- 并发请求把余额扣成负数。

本期**不要求新增兑换订单表或幂等表**。如果现有基础设施已经有幂等能力可直接复用；至少需要利用现有事务 / 行锁保证并发余额安全。

## 5. 成功响应

沿用当前 API 统一 envelope：

```json
{
  "code": 0,
  "msg": "success",
  "status": "succ",
  "data": {
    "coupon_id": 123,
    "user_card_id": 456,
    "points_cost": 200,
    "points_balance": 1280
  }
}
```

建议返回字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `coupon_id` | number | 实际兑换的券模板 |
| `user_card_id` | number | 新写入卡包的记录 id |
| `points_cost` | number | 本次实际扣减泡泡值 |
| `points_balance` | number | 兑换后的可用余额 |

H5 不要求后端把完整卡券对象塞进本接口；成功后需要完整列表时可重新读取卡包接口。

## 6. 失败响应

继续沿用项目现有规则：业务失败使用非 0 `code`，文案字段使用 `message`。

示例：

### 泡泡值不足

```json
{
  "code": 400,
  "message": "泡泡值不足",
  "data": []
}
```

### 券不可兑换 / 已下架 / 已兑完

```json
{
  "code": 400,
  "message": "当前体验包不可兑换",
  "data": []
}
```

### 未登录

```json
{
  "code": 401,
  "message": "请先登录",
  "data": []
}
```

本期不要求细分一套新的业务错误码；H5 可直接展示后端业务文案，未知错误统一显示“兑换失败，请稍后重试”。

## 7. 与现有接口的关系

### `GET /api/coupons/index`

继续作为**券模板读取接口**，不承担扣积分 / 发卡动作。

当前页面虽然保留多分类 UI，但真实可兑换能力仍以 `POST /api/coupons/redeem` 的服务端校验为准。

### `/api/userpoints/*`

H5 不应为了兑换直接调用管理型 `add/update/delete` 去拼业务流程。积分扣减由 `/api/coupons/redeem` 在服务端内部完成。

### `/api/usercards/*`

同理，H5 不直接调用 `usercards/add` 冒充兑换成功。卡包写入由兑换 action 完成。
