# 兑换卡券｜H5 ↔ 后台核兑协议（对接稿）

> 本文是 **H5 对接所需的协议约定**，不代表后台已实现或部署。由后台同事确认路径和响应口径后，H5 按确认版本联调。本卡只改 GitHub 中的 H5，不修改本地 API 工程。

## 唯一业务动作

- **建议接口：** `POST /api/cardredemptioncodes/redeem`
- **身份：** 使用项目通用 `Authorization: Bearer <accessToken>`；H5 不携带 `user_id`。
- **请求体：** `{"code":"用户输入的兑换码原值"}`。
- **输入规则：** 至少 10 位；不要求固定 12 位、不限制字母/数字字符集、不自动大写、不自动删改空格；H5 不额外限制最大长度。
- **业务语义：** 服务端检查兑换码是否可用，成功后按自己的业务规则核兑、将卡券归属当前登录用户；后端实现细节由后台同事负责。

## 响应协议

统一沿用当前 API 信封，不额外约束后台 `data` 字段：

**成功：**
```json
{"code":0,"msg":"success","status":"succ","data":{}}
```

**失败（示例）：**
```json
{"code":500,"message":"该兑换码已被使用","data":[]}
```

- 客户端只把 `code === 0` 视为成功；HTTP 200 + `code !== 0` 必须按失败处理。
- 错误提示优先使用后端 `message`，否则用通用“兑换失败，请稍后重试”。
- `401` 交给 H5 现有全局登录态失效处理。
- H5 提交中禁用重复点击；成功跳现有成功态，失败仍停留当前页供用户重试。
- Mock/preview 可以演示状态；API/test/prod 不允许演示码假成功。
- 成功后点击“查看我的卡包”走现有 `/card`；卡包实际归属和刷新响应需要后台告知已确认的券来源，不擅自把本地 UserCards/第三方 MyCoupons 两种记录合并。

## 后台同事需要核对的最小信息

1. 确认或更正用户核兑的 HTTP method 和 path；上面路径是对接建议，**不是已经确认存在**的生产路由。
2. 确认请求只需 `code`，成功判断使用标准 `code:0` 信封。
3. 确认兑换后券在哪个已对外开放的卡包接口出现，及错误文案。
4. 不需要后台同事按 H5 草稿更改事务实现方式；先把客户端合同说清楚。

**来源核对（2026-10-12，本地 API/master 只读快照）**：
现有 `/api/cardredemptioncodes` 提供通用管理 CRUD；`/api/coupons/exchange` 是泡泡值按 `id` 兑换，不是本页凭 `code` 兑换。不能把两者误接。
