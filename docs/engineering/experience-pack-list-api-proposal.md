# 体验装列表接口建议（当前最小口径）

> 状态：**Proposal / 待后端确认**
>
> 日期：2026-09-29
>
> 目标：只定义当前“体验装列表”的最小可用契约。当前业务实际上只有一个“通用体验包”；历史页面仍保留多分类 / 多体验装结构，但这不等于后端本期必须实现分类体系。

## 1. 当前业务事实

当前真实业务：

- 可展示 / 可兑换的体验装只有一个：**通用体验包**；
- H5 页面仍保留“全部 / 洗发 / 护发 / 头皮护理”等历史分类 UI；
- 这些分类属于历史设计和未来扩展位；
- **后端是否提供 `category_id`、分类表以及服务端分类过滤，当前尚未确定。**

因此本期接口验收不能把 `category_id` 当成前置条件。

## 2. 这次真正需要和后端确认的问题：category_id 要不要做

H5 历史实现里曾经把页面分类直接写成了后端主键：

```text
洗发体验 -> category_id = 2
护发体验 -> category_id = 3
头皮护理 -> category_id = 4
```

**这组 2 / 3 / 4 不是后端确认过的正式契约。** 它来自前端为了还原历史多分类页面而形成的临时假设，不能反过来要求后端照这个实现。

2026-09-29 已在 H5 侧撤回这项假设：

- 删除前端 2 / 3 / 4 的固定映射；
- `/exchange` 当前请求不再发送 `category_id`；
- MSW Mock 不再模拟 `category_id` 服务端过滤；
- 券列表 service 不再把 `category_id` 暴露为当前正式请求参数；
- 历史分类 Tab 继续保留，只作为 H5 页面结构 / 未来扩展位。

所以给后端同事的问题只有一个：

> **你们后续是否希望体验装列表支持分类？**

如果暂时不做，当前接口完全不需要 `category_id`，返回“通用体验包”即可。

如果以后决定做，再一起确认：

1. `category_id` 是否就是券分类表主键；
2. 分类有哪些；
3. id 值域是什么；
4. 通用体验包属于某一类，还是只出现在“全部”；
5. `GET /api/coupons/index` 是否按 `category_id` 服务端过滤。

在这些信息确认前，H5 不再预设任何分类 id。

## 3. 建议沿用现有列表接口

优先继续沿用已有：

```http
GET /api/coupons/index
```

当前最小请求：

```http
GET /api/coupons/index?status=10&page=1&pageSize=15
```

建议参数：

| 参数 | 类型 | 当前要求 | 说明 |
| --- | --- | --- | --- |
| `status` | number | 建议 | 当前 H5 只展示上架体验装，现有口径 `10=上架` |
| `page` | number | 可选 | 默认 1 |
| `pageSize` | number | 可选 | 默认 15，上限沿用现有接口规则 |
| `category_id` | number | **待定 / 非必需** | 后端若后续决定支持分类过滤再启用；当前验收不依赖 |

### 关于 `category_id`

当前不要求后端为配合 H5 历史分类 UI 立即新增或固定分类 id。

可以有三种后续落法，等后端方便时再定：

1. 后端不做分类：当前直接返回通用体验包即可；
2. 后端已有分类字段：后续把 `category_id` 作为可选过滤参数；
3. 后端以后再补分类：届时再一起确认 id 值域和 H5 映射。

在明确之前，文档和 H5 都不应把 `2=洗发 / 3=护发 / 4=头皮护理` 之类映射写成后端正式契约。

## 4. 当前最小响应字段

沿用项目统一 envelope：

```json
{
  "code": 0,
  "msg": "success",
  "status": "succ",
  "data": {
    "data": [
      {
        "id": 123,
        "name": "通用体验包",
        "short_desc": "适用于洗护关爱机体验",
        "image": "https://example.com/experience-pack.webp",
        "points_number": 200,
        "total_number": 1000,
        "exchanged_nuuur": 128,
        "status": 10
      }
    ],
    "current_page": 1,
    "per_page": 15,
    "total": 1,
    "last_page": 1
  }
}
```

H5 当前真正需要的字段：

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `id` | number | 体验装 / 券模板唯一 id |
| `name` | string | 卡片标题 |
| `short_desc` | string \| null | 简介 |
| `image` | string \| null | 卡片图片 |
| `points_number` | number \| string \| null | 兑换所需泡泡值 |
| `total_number` | number \| null | 总可兑换数量；当前若后端没有库存限制可按现有模型处理 |
| `exchanged_nuuur` | number \| null | 已兑换数量，保留现有字段名 |
| `status` | number \| null | 当前 `10=上架` |

### 当前不要求新增的字段

为了减小后端改动，本期不要求新增：

- `category_id`
- SKU / SPU
- 排序权重
- 商品规格
- 库存中心字段
- 兑换规则对象
- 独立“体验装类型”枚举

现有字段能支撑当前唯一“通用体验包”即可。

## 5. 列表语义

当前接口只需要回答一个问题：

> **现在 H5 可以展示哪些体验装？**

因此：

- 当前返回 1 条“通用体验包”是完全合法的正式结果；
- 返回空数组表示当前没有可展示体验装；
- H5 不应因为历史 UI 有多个分类，就要求接口必须返回多条数据；
- 分类能力以后增加时，继续复用同一列表接口即可，不需要为当前一期预建复杂模型。

## 6. H5 与分类 UI 的边界

页面的多分类 UI 保留，但它属于**前端历史结构 / 未来扩展位**。

当前联调口径：

- “全部”页能正确拿到并展示通用体验包即可；
- `category_id` 不作为后端验收条件；
- 如果后端尚未支持分类过滤，H5 不应把“分类 Tab 是否有数据”作为接口失败；
- 后续一旦后端确认分类方案，再补 `category_id` 值域和 H5 映射。

## 7. 与兑换动作的关系

本文只讨论**体验装列表**，不定义“扣泡泡值并发卡”的兑换动作。

`POST /api/coupons/redeem` 属于后续独立业务动作，需另行确认；不能因为本文存在就默认后端已经承诺实现。

## 8. 当前验收标准

后端本期做到以下几点即可满足 H5 列表联调：

1. `GET /api/coupons/index` 能稳定返回统一 envelope；
2. 当前能返回“通用体验包”；
3. 上述最小展示字段结构稳定；
4. 空列表有合法分页结构；
5. **不要求本期确定或实现 `category_id`。**

这是当前最小边界。后续业务恢复多体验装时，再增量扩展分类能力，不需要现在一次性做完。
